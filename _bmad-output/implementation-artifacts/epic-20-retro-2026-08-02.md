- **End-to-end capacity path** — Domain → migration → admin API → public API → registration lock → cache refresh → web admin + public UI shipped in one story.
- **Race-safe enforcement** — `FOR UPDATE` on activity row inside transaction; concurrent last-spot integration test covers the hot path.

## What we learned

- **EF migrations need Designer.cs** — Missing `AddActivityMaxRegistrants.Designer.cs` blocked migration apply locally until fixed (`e6ec371`).
- **PostgreSQL quoted identifiers** — Raw SQL `SELECT id FROM activities` failed; required `"Id"` for FOR UPDATE lock (`f1aa566`).
- **Plan limits are a separate concern from activity caps** — Story 20.1 scoped plan limits out; operators still expect caps ≤ plan monthly limit. Validate at save time, not only at registration.
- **Client validation must not depend on shell alone** — Server is source of truth; UI should wait for shell, block on shell error, and surface API ProblemDetails on failure.
- **Grandfather unchanged caps on update** — Branding panel resubmits `maxRegistrants`; plan validation must skip when value unchanged so legacy over-plan rows do not block unrelated edits.
- **Deploy drift looks like product bugs** — Feature on branch but `main` Docker = “issue still persists.” Merge + `--force-recreate api web nginx` is mandatory verification step.

## Key insights

1. **Two limits, two enforcement points** — Per-activity cap (`MaxRegistrants`) vs tenant monthly plan (`TenantAccessService`). Document clearly in admin copy: “monthly plan usage still applies.”
2. **Validation belongs in ActivityService + shared validator** — `ActivityCapacityValidator` reused by unit tests, service, and web `activity-capacity-limits.ts`.
3. **Full-replace PUT requires UI discipline** — All update panels must preserve `maxRegistrants` or use partial endpoints; branding panel already preserves cap.
4. **Story “done” ≠ operator verified on main** — Sign-off checklist: merge → pull main → rebuild containers → manual test on target tenant plan.
