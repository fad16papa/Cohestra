## Team retrospective (facilitated)

### What went well

- **Design → public → outbound loop closed** — Operators configure once in Design tab; public page, share kit, and confirmation email now share `RegistrationThemeResolver` + query helpers instead of divergent hero logic.
- **Code review caught real data-loss bugs** — Community rename wiping brand kit, preview inherit flag mismatch, and `section_header` validation gaps were fixed before wide release (`epic-25-code-review-2026-08-12.md`).
- **Incremental polish PRs stayed small** — Dark preview text (#192), publish gate (#193), email hero (#198), and touchpoints hardening (#199) each merged quickly with focused diffs.
- **PRD before hardening** — Registration touchpoints PRD (#199) documents the “one resolver, multiple renderers” contract so SMS/calendar do not repeat the email hero bug.
- **Marketing tier clarity** — Enterprise card now reads “Everything in Pro” plus customs (#200); pricing copy matches backend limits audit.
- **UX motion with accessibility guardrails** — Card hover system uses `@media (hover: hover)` and `prefers-reduced-motion` (#201).

### Challenges and growth areas

- **Sprint-status drift (again)** — Epic 25 merged to `main` while tracker still listed stories `review`. Same pattern as Epics 23–24 early in sprint.
- **Surface drift until PR #198** — Live registration showed hero; email used platform SVG header. Required explicit touchpoints PRD + shared queries to prevent recurrence.
- **Deferred cache invalidation** — Community brand-kit update may lag on public activity cache until activity refresh (documented in code review defer list).
- **Logo asset tenant ownership** — Public asset URLs lack tenant ownership check (deferred v1).
- **CI .NET job intermittent** — Marketing PR #200 showed .NET build failure while Next.js and integration passed; marketing-only changes should not block on unrelated backend flakes.
- **Story batch 25.3–25.5 in one commit** — Harder to review atomically than 25.1/25.2 separation; future epics should keep one story per merge when possible.

### Key insights

1. **Touchpoints are part of the feature** — A beautiful public registration page fails if confirmation email shows a black bar and broken logo. Schedule touchpoint stories (or PRD) alongside renderer work.
2. **Shared query helpers beat copy-paste resolution** — `CommunityQueries` + `RegistrationThemeQueries` centralize inherit logic for API, email, and web.
3. **Publish gate protects operator trust** — Blocking publish when Form/Design tabs have unsaved changes prevents “live site ≠ preview” support tickets.
4. **Docs + tracker sync is a shippable task** — Mark epic done and retro complete in `sprint-status.yaml` when last PR merges, not when conversation ends.
5. **Landing polish compounds conversion** — Pricing card parity, hover affordances, and mobile carousel scroll are low-risk, high-signal marketing improvements.

## Team agreements

- **One resolver, multiple renderers** — Public page, share kit, email (and future SMS/calendar) use shared theme resolution; no surface-specific hero hacks.
- **Publish gate stays on** — Do not publish activities with unsaved Form or Design tab changes.
- **Registrant copy ≠ admin copy** — Public limit messages stay plan-neutral; admin surfaces may show plan context (Epic 24 lesson holds).
- **Merge → sync sprint-status** — Epic marked done when last story PR merges to `main`.
- **Marketing cards: motion-safe hover** — Desktop pointer only; respect reduced motion.

---

## Key takeaways

1. Registration experience is not done until **outbound touchpoints** match the public page.
2. **Tracker drift** remains a systemic issue — sync sprint-status on merge.
3. **Small polish PRs** (email, mobile, marketing) compound trust and conversion without epic scope creep.
4. **Deferred infra items** (cache invalidation, asset ownership) should be scheduled before production scale, not after first incident.
