Approach

Technique: Slice decomposition + failure-mode walk

Each slice is a shippable product increment, not a theme. For every slice: problem, user story, in-scope fields/surfaces, data model, API, UI, acceptance tests, non-goals, failure modes, effort shape.

Session insight: Slice A is the only slice that is unambiguously “steal Tally’s capture UX on Cohestra’s existing form.” B and C change distribution or schema semantics. File upload / draft-as-client / HMAC webhooks stay later because they expand the Client contract or ops surface.

Slice A — Native capture depth

One-liner: Make the existing activity registration form as good as a Tally one-pager for the fields Cohestra already understands — without logic, embed, or website contact.

Why first: Highest Tally gap vs smallest architecture change. Same Form tab, same public URL, same Client mapping.

A1 Hidden / UTM fields

New field type hidden (or utm). Not shown to the registrant. Value from query string (?utm_source=ig) or a constant set in the builder (campaign id). Stored in Registration.Answers and optionally copied onto Client tags / notes.

Why Tally: Tally Hidden Fields are the whole attribution story. Cohestra has none today.

Failure: PII in query strings logged in nginx — document; don’t put emails in UTM. Missing params → empty answer, still submit.

A2 Textarea

New type textarea mapped like text to Client.Notes or a named custom answer. Distinct from single-line text for “why are you joining?”

Failure: 2k/5k char cap; sanitise XSS on display in registrations table.

A3 Date

Type date with ISO date storage. Use for DOB, preferred session date, “when did you last attend.” Maps to Client.DateOfBirth when labelled as such, else Answers only.

Failure: Timezones — date-only, no datetime. Min/max optional later.

A4 Thank-you piping + email piping

Thank-you copy and confirmation email already exist. Add merge tokens: {{firstName}}, {{activityTitle}}, {{startDate}} from Activity + submitted answers. Same token set in both places so operators don’t learn two languages.

Failure: Unknown tokens left as-is or stripped — pick one and test. Don’t allow HTML in operator-authored thank-you without sanitisation.

A5 Closed-state copy + close-at

Today closed/full/ended shows generic copy. Add operator-editable closed message + optional registrationClosesAt datetime independent of activity end (e.g. close 48h before class).

Failure: Clock skew — server time only. Capacity vs close-at: both can block; message should say which.

A6 Form-tab UX: slash-add, not DnD

Keep list editor. Add “Add field” that inserts after focused field (slash or +). Reorder via up/down. Matches UX-DR32 (no canvas DnD) and Tally’s insert-in-place feel.

A7 Operator email on new registration

Notify tenant email (or activity owner) when a registration is submitted. Template with name, activity, link to registration row. Completes Tally’s “you get the lead” loop without webhooks.

Failure: Don’t email on every field edit. Rate-limit / digest optional later. Honor existing email infrastructure (SendGrid).

A8 Optional: bot friction

Turnstile/hCaptcha on public POST. Not Tally-clone; ops hygiene. Can ship with A or immediately after. Failure: false positives on mobile; provide operator override / allowlist later.

Slice A non-goals: visibleWhen, multi-step, iframe, website contact, file upload, webhooks.

Acceptance (A): Hidden UTM round-trips; textarea + date in schema + public form + answers; thank-you shows first name; closed copy shows when closed; operator receives email; Form tab can insert field without DnD.

Slice B — Recipes + optional steps

One-liner: Cover ~80% of Tally logic with 3–5 named recipes, plus an optional Identity → Details → Consent stepper that is still one schema.

B1 visibleWhen recipes

JSON on a field, e.g. visibleWhen: { recipe: "equals", fieldId: "role", value: "parent" }. Recipes: equals, notEquals, isChecked, isNotEmpty. No formula language, no AND/OR tree in v1 (AND of two equals can be a later recipe).

Server: Ignore hidden field values on submit (don’t persist spoofed answers for invisible fields). Client: hide/show without page reload.

Failure: Circular refs (A shows if B, B shows if A) — builder validation. Required + hidden = not required.

B2 Optional 3-step

Activity flag registrationSteps: identity | details | consent grouping existing fields. Progress 1/3. Back doesn’t lose data. One POST at the end (or save draft in session only — not a Client until submit).

Failure: Don’t invent a generic wizard builder. If operators need 7 steps, that’s a different product.

Slice B non-goals: Calculated fields, jump-to-page, payment inside form, logic IDE.

Depends on: Slice A field types exist so recipes have something to hide.

Slice C — Embed + website contact

One-liner: Registration and/or a Contact block can live on a Cohestra website (or later a foreign site) without cloning Tally as a platform.

C1 Activity embed

Today CSP frame-ancestors 'none' blocks iframes. Options: (1) dedicated embed route with relaxed CSP + nonce, (2) same-origin website section that mounts the existing public form component (no iframe). Prefer (2) for Cohestra sites; (1) only if tenants must embed on Squarespace/etc.

Failure: Clickjacking if CSP too open — allowlist tenant website domain or embed token. Theme: inherit website tokens, not a second design system.

C2 Website Contact → Client

Website section type: name, email, phone, message, consent. POST creates Client + optional Registration against a “contact” activity or a dedicated ContactSubmission that still upserts Client. This is the Tally “contact form on my site” job, mapped to Cohestra’s object.

Failure: Duplicate clients — reuse existing email/phone dedup. Don’t create a second CRM.

Slice C non-goals: Public form marketplace, embed on arbitrary sites in v1 unless (1) is explicitly in scope, Tally-style share page.

Later D / E / F (not v1)

Same depth as A–C so “maybe” is not a shrug. Do not smuggle into Slice A.

D — File upload

Type file: waiver PDF / ID photo. Signed upload URL, MIME + size cap, virus scan, GDPR delete with the Client. Admin download on the registration row.

Why later: storage + security epic wearing a field-type costume.

E — Draft-as-client

Abandoned Identity step becomes an Incomplete Client. Beats Tally — and pollutes CRM unless consent, retention, and capacity rules are explicit. Default: off. Session-only answers (no Client) is the safe way to help Slice B bounce.

F — HMAC tenant webhooks

Outbound registration.created with HMAC, retries, delivery log, SSRF guard. A7 email covers most hosts. Build when a tenant asks for Zapier-out — not to look like Tally. No inbound webhooks.
